# GAS単体構成：Webhook の調査結果と設計

## 1. 調査結果（2026-10-21）

### 1-1. 本番ウェブアプリの応答

ID管理シートの `GAS_WEBAPP_URL`（`…AKfycbwNho2m…/exec`）に、ブラウザから**認証情報なし**（`credentials: 'omit'`）でリクエストを送りました。

| リクエスト | 結果 |
|---|---|
| GET | 302 → `script.googleusercontent.com/macros/echo` → 200 `{"ok":true,"service":"SKY STANDARD LINE",…}` |
| POST（LINE の検証と同じ形 `{"destination":…,"events":[]}`） | 302 → echo → 200 `{"ok":false,"error":"signature_required"}` |

結果からわかったこと:

- 公開設定は「全員」で正しく動作しています（ログイン画面への 302 ではありません）。
- doPost は実行されています。ただし応答が ContentService なので 302 になり、LINE はリダイレクトを追わないため「302 で失敗」になります。
- 当時のコードは、署名のない直接 Webhook を `signature_required` で拒否していました。302 とは別に、メッセージ自体も処理されていなかったことになります。

### 1-2. 応答方式による HTTP ステータス（検証用プロジェクトで実測）

ユーザーの許可を得て、検証用プロジェクト「SKY STANDARD 302検証（削除可）」を一時的にデプロイし、匿名アクセスで POST しました。デプロイは計測後にアーカイブ済み（404）です。プロジェクト自体は Google ドライブに残っているので、不要なら削除してください。

| doPost の戻り値 | POST の HTTP ステータス | GET |
|---|---|---|
| `ContentService…setMimeType(JSON)` | 302（リダイレクト） | 302 |
| `ContentService.createTextOutput()` | 302 | 302 |
| `HtmlService.createHtmlOutput()` | **200**（リダイレクトなし） | 200 |
| 何も返さない | 200（「スクリプトが完了しましたが、何も返されませんでした」というエラーページ） | 200 |

### 1-3. リクエストヘッダー

`X-Line-Signature` を付けて POST したときの doPost の `e` には、次のキーしかありませんでした。`e.headers` はありません。

```text
contentLength, contextPath, parameter, parameters, postData, queryString
```

→ **GAS 単体では LINE の署名を検証できません。**

### 1-4. 未確認の点

- LINE プラットフォーム（LINE のサーバー）からのリクエストでも、HtmlService の応答が 200 と判定されるかは未確認です。ブラウザからの実測では 200 でした。
- 確認方法: 新コードをデプロイした後、管理メニュー「初期設定 → LINE接続チェック」で疎通テストを実行します。LINE の Webhook テスト API の結果と、GAS 側の受信記録を表示します。

## 1-5. 再調査：302 が続いた確定原因と LINE 側の検証結果（2026-10-21 14:40〜14:52 JST）

| 確認対象 | 結果 |
|---|---|
| GitHub `feature/line-system` | `0ec6ad5`（HtmlService 応答あり） |
| ローカル（Mac） | `0ec6ad5`（同上） |
| GAS エディタ（本体GAS） | **`a23fac1` と12ファイルすべてが SHA-256 で完全一致**＝`0ec6ad5` が反映されていない |
| 本番デプロイ | バージョン3（14:38）＝エディタと同じ旧コード。空イベントの POST は 302 → echo で `signature_required` |

**確定原因**: 修正コード（`0ec6ad5`）が本体GASに反映されておらず、本番の Web アプリは旧コード（ContentService で応答＝302）のまま動いていた。

**実施した反映（ユーザー承認済み）**:
1. 本体GASの変更6ファイルを `0ec6ad5` の内容に置き換えました（GitHub の該当コミットから取得し、SHA-256 を照合）。
2. 保存後、再読み込みして12ファイルの一致を確認しました。
3. 既存デプロイを「新バージョン」で更新しました（**バージョン4**、14:48、URL は同じ）。

**反映後の実測**:
- 空イベントの POST（`{"destination":…,"events":[]}`、認証情報なし、リダイレクトを追わない）: 反映直後は 302 と 200 が混在し、約1〜2分後からは **6回連続で HTTP 200**（リダイレクトなし）。デプロイの切り替えには少し時間がかかります。
- LIFF API 形式（JSON 応答）: 従来どおり 302 → 追従で `auth_failed`（想定どおり）。
- GET: 302 → echo → 200 の JSON（GET の成功は Webhook POST の成功を意味しません）。

**LINE 側の検証（LINE Messaging API の Webhook テスト。管理メニュー「LINE接続チェック → 疎通テスト」で実行）**:
- `【OK】LINE 側の疎通テスト結果: 成功（HTTP 200 OK）`
- `【OK】GAS 側の受信記録: テスト中に受信を確認`（最終受信 2026/10/21 14:51:12）
- Webhook の利用: オン。Webhook URL は ID管理の `GAS_WEBAPP_URL` と一致。

LINE Developers コンソールの「検証」ボタンも、同じテスト API の結果を表示します。ただし、コンソール画面上での表示は確認していません。

**再発防止**: `APP.BUILD`（コードの版）を doGet が返すようにしました。管理メニューの「LINE接続チェック」「接続・設定診断」は、保存済みコードと本番 Web アプリの版を比較し、不一致なら【NG】で「新バージョンのデプロイ」を案内します。

## 2. 設計

| 項目 | 内容 |
|---|---|
| 受信方式 | `WEBHOOK_MODE` 未設定（direct）のとき、LINE からの直接 Webhook を受け付ける |
| 応答 | LINE Webhook には HtmlService（200）。LIFF・予約イベントは従来どおり JSON |
| 信頼度 | direct で受けたイベントは「未検証」。リレー経由（HMAC）は「署名検証済み」 |
| 形式検証 | 宛先・イベント数・ID・時刻・送信元・応答トークン・本文長・postback 長を検証し、不正なものは処理しない |
| 重複防止 | `webhookEventId` を 6 時間保持し、ロック内で確認・登録（従来どおり） |
| 記録・通知 | 未検証イベントでは、応答（reply）が LINE に受理された後にのみ実行（応答トークン確認） |
| unfollow | 未検証イベントでは、プロフィール API の 404 で友だちでないと確認できた場合のみ反映 |
| 重要操作 | 予約状態の変更（HMAC 予約イベントのみ）、個人情報の開示（LIFF＋ID トークンのみ）、管理操作（管理メニューのみ）は Webhook から到達不能 |
| 診断 | 受信記録（`LAST_WEBHOOK_AT`）と、LINE の疎通テスト結果を分けて表示 |

## 3. 応答トークン確認の考え方と限界

- LINE の応答トークンは、LINE がイベントごとに発行する1回限りの値です。偽造イベントに含まれる適当なトークンは、reply API に拒否されます（HTTP 400）。
- そこで、記録や外部通知を伴う処理は「先に応答して、受理されたら記録する」順序にしました。これにより、偽造イベントで問い合わせを登録したり、運営通知を送らせたりすることを防ぎます。
- この確認でわかるのは「その応答トークンが有効だった」ことだけです。イベント本文（ユーザーID・テキスト）が LINE の送ったものと一致するかは保証しません。本物の応答トークンを第三者が入手する経路は通常ありませんが、署名検証と同等ではありません。
- 偽造リクエスト自体は受け付けてしまいます。その結果、次の影響は防げません。
  - GAS 実行時間・URL Fetch 割り当ての消費（偽造イベント1件につき reply API 呼び出し1回）
  - 受信記録の更新

## 4. 再送と失敗時の扱い

- GAS単体構成では、LINE に常に HTTP 200 を返します。そのため、応答前に一時的なエラー（LINE API の 5xx など）が起きても、LINE から再送されません。そのイベントは失われます（実行ログに `webhook.event_failed` が残ります）。
- 応答した後に問い合わせの保存が失敗した場合は、運営に「保存失敗」を通知します。手動でシートに追記してください。
- 予約イベント（予約サイト → GAS）は、署名付き・冪等で、予約サイト側から再送できます（[architecture.md](architecture.md)）。

## 5. 署名検証が必要になったら

`src/relay/` の署名検証リレーを任意のサーバー（Cloud Run 等）で動かし、`WEBHOOK_MODE=relay` と `RELAY_SHARED_SECRET` を設定します。LINE の Webhook URL はリレーの `/webhook` に変更します。この場合、イベントは「署名検証済み」として扱われ、直接 Webhook は処理しません。
