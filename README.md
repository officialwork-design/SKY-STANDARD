# SKY STANDARD 公式LINEシステム

ヘリコプター遊覧飛行・チャーター事業「SKY STANDARD」の LINE 公式アカウントを、予約導線・予約確認・顧客対応の営業チャネルとして運用するためのシステムです。

**標準構成は「LINE公式アカウント → Google Apps Script → Googleスプレッドシート」です。** Cloud Run・Firebase・外部の有料サーバーは使いません。ただし GAS 単体では、LINE の署名（`X-Line-Signature`）を検証できません。この制約と対策は[9章](#9-line-署名検証ができないことによる制約)に記載しています。

### 予約確認の処理フロー

```text
［予約確認］をタップ（postback a=rsv_start、1対1トークのみ）
  └▶ 予約IDの入力案内（入力待ち 10分。［入力をやめる］／メニュー操作で中断）
      └▶ 予約IDを送信
          ├ 形式が違う（SKY-YYYYMMDD-XXXXXX 以外）→ 再入力（3回で終了・オペレーター導線）
          ├ 本人確認方式が未設定（RESERVATION_CHECK_MODE が空欄・OFF＝既定）
          │    → 検索せず「表示は準備中」＋［オペレーターに相談］（予約IDを添える）
          └ RESERVATION_CHECK_MODE=LINE_LINKED
               → 「予約管理」シートを予約IDで検索
                  ├ 1行だけ一致 かつ LINEユーザーID＝問い合わせた LINE アカウント → 予約内容を返信（＋予約変更・キャンセル・オペレーター）
                  ├ 該当なし／他人の予約／LINEユーザーID が空欄 → 同じ文面で「確認できませんでした」＋オペレーター（存在の有無を答えない）
                  ├ 同じ予約IDの行が複数 → 表示しない（同上の案内）＋エラーログに記録
                  └ シートがない・必要な列がない・読み取り失敗 → 「ただいま確認できません」＋オペレーター＋エラーログ
```

返信する項目：予約ID／予約日（搭乗日）／予約時間（時間帯）／プラン名／人数／予約ステータス。氏名・電話番号・メール・金額・決済情報は表示しません。予約内容は応答（reply）でだけ送り、プッシュでは送りません。グループ・複数人トークでは予約確認を受け付けません。

予約変更・キャンセルのボタンは GAS では予約を変更・取消しません（担当者・予約サイトの手続きへ案内）。

### 本人確認方式

| `RESERVATION_CHECK_MODE`（ID管理） | 動作 |
|---|---|
| 空欄・`OFF`（既定） | 予約内容を表示しない。予約IDを添えてオペレーターへ案内 |
| `LINE_LINKED` | 「予約管理」の LINEユーザーID と、問い合わせた LINE アカウントのユーザーID（LINE が発行し、利用者は変更できない）が一致する予約だけ表示 |

- 予約IDだけでは開示しません。LINEユーザーID は、予約時に LINE ログイン等で取得するか、担当者が本人と確認したうえで入力する前提です。この運用が決まるまで `OFF` のままにしてください。
- 予約サイト API（`RESERVATION_API_BASE_URL`）を設定した場合は、未紐づけの予約を電話番号・メールで照合する追加確認も使えます（今回は対象外。仕様は [docs/reservation-api.md](docs/reservation-api.md)）。
- Webhook は GAS 単体で受信するため署名を検証できません。予約内容は「LINE が受理した応答トークン」への返信でだけ送るため、偽装リクエストでは受け取れません（[9章](#9-line-署名検証ができないことによる制約)）。

## 0-2. LINE 監視・操作ログ・設定診断（2026-11-06 追加）

### 概要

「GAS の実行は完了なのに LINE に返信が届かない」原因を、管理者がスプレッドシートで確認できるようにする仕組みです。GAS の実行履歴の「完了」は、`doPost` が例外なく終わったことしか示しません。返信しなかった（設定で止めた）場合や、LINE が返信を受け付けなかった場合も「完了」になります。そこで次の3つを分けて記録します。

| 仕組み | 記録先 | 内容 |
|---|---|---|
| LINE操作ログ | 「LINE操作ログ」シート（新規） | Webhook イベントごとに、受信 → 処理の開始 → LINE 返信 API の成否 → 終了（正常終了／返信なし／設定により停止／異常終了） |
| エラーログ | 「エラーログ」シート（既存＋6列） | 障害（ERROR／FATAL）、注意（WARNING）、設定による意図的な停止（CONFIG_WARNING）を原因コード付きで |
| LINEシステム診断 | 管理メニュー（画面に表示） | Webhook・LINE 認証・予約確認・問い合わせ・リッチメニューの設定と、直近のログ件数（読み取り専用） |

**返信成功**は「LINE の返信 API が HTTP 200 を返した」ことです。利用者の端末に表示されたこと（到達・既読）までは確認できません。

### 2026-11 の無反応の原因経路

「問い合わせ管理」の **自動返信有効** が `FALSE` の顧客には、`dispatchEvent_` の最初の判定（`isOperatorMode_`）で有人対応中と判断されます。その後は `handleOperatorModeEvent_` で、リッチメニュー・予約確認・お問い合わせ・FAQ を含むすべての自動返信を止めます。これは「有人対応中は自動返信が割り込まない」ための仕様です。ただし以前は実行ログ（INFO）にしか残らず、`doPost` は「完了」になるため原因を特定しにくい状態でした。現在は次のように記録します。

- LINE操作ログ：その顧客のイベントごとに「設定により停止／AUTO_REPLY_DISABLED」
- エラーログ：重要度 `CONFIG_WARNING`、原因コード `AUTO_REPLY_DISABLED`、関連設定キー `問い合わせ管理:自動返信有効`、関連ID（判定行の受付ID）。同じ顧客・同じ受付IDにつき6時間に1件
- LINEシステム診断：「N 名の顧客の自動返信が停止中です（判定行の受付ID：…）」

### セットアップ手順

1. 本体GASを反映（下の「デプロイ手順」）。管理メニュー（`src/sheet-admin/Code.gs`）にも「LINEシステム診断」を追加したため、管理メニュー用GASも更新します。
2. 管理メニュー「初期設定 → シート列・設定行の補完」を実行します。
   - 「LINE操作ログ」シートを作成します（7列）。
   - 「エラーログ」に不足列を末尾に追加します（6列。既存の行・列は変更しません）。
   - 実行しなくても、最初の記録時に自動で作成・補完されます。
3. 「システム管理 → LINEシステム診断」を実行し、【要対応】がないことを確認します。

LINE ユーザーID・メッセージ本文・表示名・電話番号・メール・トークンは保存しません。同じイベントの再送（同じ `webhookEventId`）は処理済みとして記録しません。1イベントの行は処理の終わりに1回でまとめて書き込みます。

**1操作（1イベント）あたりの行数**：3〜7行（通常4〜5行）。行の構成は「受信」＋「開始」（処理の振り分け）＋機能ごとの段階（0〜3行）＋「返信成功／返信失敗」（返信した場合）＋最終結果（1行）です。

| 操作 | 行数 | 処理結果の並び |
|---|---|---|
| 友だち追加・お問い合わせメニュー・準備中ボタン・テキスト（FAQ 等の自動応答） | 4 | 受信 → 開始 → 返信成功 → 正常終了 |
| 予約確認の開始・問い合わせ項目の選択・問い合わせの受付 | 5 | 受信 → 開始 → 開始（機能の段階）→ 返信成功 → 正常終了 |
| 予約IDの入力（`RESERVATION_CHECK_MODE=OFF`） | 5 | 受信 → 開始 → 設定により停止 → 返信成功 → 正常終了 |
| 自動返信有効=FALSE の顧客の操作 | 3 | 受信 → 設定により停止 → 設定により停止（最終） |
| 未対応の postback | 4 | 受信 → 開始 → 対象外 → 返信なし |
| 予約検索の失敗・予約ID重複 | 6 | 予約IDの入力に「失敗」の段階が1行加わる |
| 問い合わせ受付で保存・運営通知が失敗 | 6〜7 | 失敗した段階ごとに「失敗」が1行加わる |
| 返信 API の失敗・処理中の例外 | 3〜5 | …→ 返信失敗 → 異常終了 |
| 再送（同じ webhookEventId）・偽装／期限切れの応答トークン | 0 | 記録しない（後者はエラーログの WARNING のみ） |

**エラーログに追加した列**：イベント種別／追跡ID／原因コード／処理結果／関連設定キー／HTTPステータス（既存の「重要度」がログレベル、「発生元」が機能名、「エラーメッセージ」がエラー内容）

**ログレベル**：`FATAL`／`ERROR`（障害）、`WARNING`（要確認。例：未対応の postback、返信なし、偽装・期限切れの応答トークン）、`CONFIG_WARNING`（設定による意図的な停止。障害ではない）

**原因コード**

| 原因コード | 意味 |
|---|---|
| `LINE_API_400` / `LINE_API_400_INVALID_REPLY_TOKEN` | LINE API のリクエスト不正／応答トークンの期限切れ・偽装 |
| `LINE_API_401` / `LINE_API_403` / `LINE_API_404` | トークン無効／権限なし／対象なし |
| `LINE_API_429` / `LINE_API_5XX` / `LINE_API_HTTP_ERROR` / `LINE_API_NETWORK` | 回数超過／LINE 側障害／その他の HTTP エラー／通信エラー |
| `WEBHOOK_EXCEPTION` / `INTERNAL_ERROR` | Webhook 処理中の例外／その他の内部エラー |
| `CONFIG_MISSING` / `CONFIG_INVALID` | 必須設定の不足／設定値が不正（関連設定キー列に対象キー） |
| `AUTO_REPLY_DISABLED` | 自動返信有効=FALSE のため返信しない（CONFIG_WARNING） |
| `RESERVATION_CHECK_OFF` | 予約内容の表示は OFF（正常な運用。LINE操作ログのみ） |
| `RESERVATION_FAILED` / `RESERVATION_DUPLICATE_ID` | 予約確認の検索失敗／予約IDの重複 |
| `INQUIRY_FAILED` / `NOTIFY_FAILED` | 問い合わせの保存失敗／運営通知の失敗 |
| `UNSUPPORTED_POSTBACK` | コードが処理できない postback（古いリッチメニュー等） |
| `NO_REPLY` | 返信が必要なイベントに返信しなかった（上記以外） |
| `REPLY_TOKEN_REUSED` | 同じ応答トークンへの2回目の返信を止めた |

### トラブルシュート

| 症状 | 確認すること |
|---|---|
| GAS は「完了」なのに LINE が無反応 | LINE操作ログでそのイベントの最終行を見る。「設定により停止」→ 原因コード（`AUTO_REPLY_DISABLED` なら自動返信有効）。「返信なし」→ `UNSUPPORTED_POSTBACK` 等。「返信失敗」「異常終了」→ 追跡IDでエラーログの原因コード・HTTPステータス |
| 設定が FALSE になっている | 診断の「問い合わせ・自動返信」に停止中の受付IDが表示される。有人対応が終わっていれば、その行の自動返信有効を TRUE に（または管理メニュー「選択中の顧客の自動返信を再開」） |
| Webhook が届かない | LINE操作ログに行が増えない。GAS には記録されないため、診断の「Webhook」（Webhook の利用・URL の一致・Web アプリの版・最終受信時刻）と LINE Developers の「検証」で確認 |
| LINE API で送信失敗 | エラーログの原因コード：401 はトークン再発行、429 は送信数・回数、5XX は LINE 側障害（時間をおく）、`LINE_API_400_INVALID_REPLY_TOKEN` は応答トークンの期限切れ・偽装 |
| リッチメニューが古い | 診断の「リッチメニュー」：処理できないボタン（`UNSUPPORTED_POSTBACK`）、登録内容と設定の不一致 →「リッチメニュー設定確認」→ 承認後に「リッチメニュー登録・更新」 |
| ログが記録されない | 「シート列・設定行の補完」でシートを作成。シートの保護・権限、`SPREADSHEET_ID` を確認。ログの書き込みに失敗しても返信は止まらない（実行ログに `oplog.write_failed` / `errorlog.write_failed`） |

**計測できない範囲**：URL を開くタイプのボタン（ご予約はこちら・よくある質問）は LINE が直接ページを開き、Webhook が発生しないため GAS では記録できません。タップ数を測るには、Web 側の計測（アクセス解析、URL にパラメータを付けるなど）が必要です。

## 8. HTTP 302 の原因と対応

**原因（2026-10-21 に実測）**

- GAS の Web アプリは、`ContentService`（JSON・テキスト）で応答すると **HTTP 302** を返し、`script.googleusercontent.com/macros/echo` へリダイレクトします。doPost 自体はリダイレクト前に実行されています。
- LINE はリダイレクトを追わないため、「302 で失敗」と表示します。
- 当時の本番ウェブアプリも、匿名アクセスで POST すると 302 を返しました。リダイレクト先には doPost の出力（旧コードの `signature_required`）がありました。つまり公開設定（全員）は正しく、ログイン画面への 302 ではありません。
- 旧コードは署名なしの直接 Webhook を拒否していました。そのため 302 とは別に、メッセージは処理されていませんでした。
- 検証用プロジェクトで応答方式ごとに実測した結果は次のとおりです。

| 応答 | HTTP ステータス |
|---|---|
| ContentService（JSON） | 302 |
| ContentService（テキスト） | 302 |
| **HtmlService** | **200**（リダイレクトなし） |
| 何も返さない | 200（ただし本文はエラーページ） |

**対応**

- LINE からの直接 Webhook には **HtmlService で応答**するよう変更しました。LIFF と予約イベントの応答は、従来どおり JSON（302→追従）です。
- ブラウザの `fetch` などリダイレクトを追うクライアントでは、302 でも問題ありません。

**302 が続いた確定原因（2026-10-21 再調査）**

- HtmlService 対応のコード（`0ec6ad5`）は GitHub にはありましたが、本体GASに反映されていませんでした。エディタも本番デプロイ（バージョン3）も、旧コード `a23fac1` と完全に一致していました。
- 反映してバージョン4でデプロイした後、LINE の Webhook テスト API で **成功（HTTP 200 OK）**、GAS 側の受信記録も確認しました。詳細は [docs/gas-only.md](docs/gas-only.md#1-5-再調査302-が続いた確定原因と-line-側の検証結果2026-10-21-14401452-jst)。
- 再発防止のため、管理メニューの「LINE接続チェック」「接続・設定診断」が、本番 Web アプリの版（doGet の `build`）と保存済みコードの版を比較します。

詳細: [docs/gas-only.md](docs/gas-only.md)

## 9. LINE 署名検証ができないことによる制約

GAS の `doPost(e)` には HTTP ヘッダーが渡されません（実測した `e` のキーは `contentLength, contextPath, parameter, parameters, postData, queryString` のみ）。そのため `X-Line-Signature` を検証できず、**受け取った Webhook が本当に LINE から来たものかを暗号学的に確かめられません**。Web アプリの URL を知っている人は、LINE を装ったリクエストを送れます。URL を秘密にしても、トークンを付けても、署名検証の代わりにはなりません。

そこで GAS単体構成では、直接届いたイベントを**すべて「未検証」**として扱い、次の制限を設けています。

| 処理 | 未検証イベントでの扱い |
|---|---|
| FAQ・キーワード自動応答 | 実行します。応答だけで記録は伴いません。偽造イベントの応答トークンは LINE が拒否します |
| 顧客登録（友だち追加） | あいさつの応答が LINE に受理された場合のみ登録します |
| 問い合わせ保存・運営通知 | 受付返信が LINE に受理された場合のみ、保存・通知します |
| オペレーター対応の開始 | 受付返信が LINE に受理された場合のみ開始します。**再開は Webhook からは不可**（シートの「自動返信有効」=TRUE か管理メニューのみ） |
| 「担当者に送る」用の一時保存・入力待ち状態 | 応答が受理された場合のみ |
| ブロック反映（unfollow） | プロフィール API で「友だちでない」と確認できた場合のみ |
| 予約確定・決済完了・キャンセル等の状態変更 | **Webhook からは不可**。予約サイトの HMAC 署名付きイベントのみで行います |
| 予約内容の表示（LINE トークの予約確認） | LINE アカウントに紐づく予約、または予約サイト API で電話番号・メールが一致した予約だけを、**応答（reply）でのみ**表示します（偽装イベントの応答トークンは LINE が拒否するため第三者には届きません）。氏名・連絡先・金額は表示しません |
| 予約の変更・キャンセル | **Webhook からは不可**。予約サイトの手続き画面または担当者へ案内するだけです |
| 管理者操作（通知承認・リッチメニュー更新等） | **Webhook からは不可**。管理メニュー＋`ADMIN_USERS` のみで行います |

応答トークンによる確認は**補助的な対策**で、署名検証と同等の保証ではありません。ただし、LINE が発行する1回限りのトークンが偽造イベントでは使えないことを利用しており、偽造による記録・通知の大半を防ぎます。残るリスクは[12章](#12-残っているセキュリティリスク)を参照してください。

## 12. 残っているセキュリティリスク

- **偽造 Webhook の受信**: URL を知る人は偽のイベントを送れます。応答トークン確認により記録・通知は抑止されますが、次の影響は残ります。
  - 受信記録の更新
  - GAS の実行時間・URL Fetch 割り当ての消費（大量送信による妨害）
  - ログの増加
- **応答トークン確認の限界**: LINE が発行した本物の応答トークンを第三者が入手した場合（通常は起こりません）、その1回分は防げません。イベント本文の改ざんも検知できません。
- **予約確認の本人確認（電話番号・メールの照合）**: 照合は応答の前に予約サイト API へ送ります。偽装イベントでも照合 API が呼ばれ、回数制限を消費しうるため、予約サイト側で予約IDごと・LINE ユーザーごとの回数制限を必ず設けてください（照合結果の予約内容は応答でしか返さないため、第三者には届きません）。
- **予約確認の表示範囲**: 予約サイト API がない間は「予約管理」シートの LINE ユーザーIDで本人を判断します。シートの LINE ユーザーIDを編集できる人は、表示対象を変えられます。
- **スプレッドシート編集者**: 管理メニュー用GASを編集できるため、管理者がメニューを実行したときに管理者権限で任意の処理を実行させることが可能です。編集権限は信頼できる担当者に限定してください。
- **Web アプリは「全員」公開**: LIFF・予約イベントは ID トークン・HMAC で認証しています。管理操作は Web アプリからは実行できません。

## エラーログ

本体GASで発生したエラー（ERROR / FATAL）だけを、「エラーログ」シートに記録します。INFO・WARN、正常な受信・送信は記録しません。

- 同じエラーは10分（FATAL は1分）に1件だけ記録します。
- 機密情報（トークン・本文・LINE ユーザーID・メール・電話番号）は記録しません。
- ログの書き込みに失敗しても、本来の処理は止まりません。
- 過去の実行履歴のエラーは取得できません（Apps Script API の制約）。

詳細: [docs/errorlog.md](docs/errorlog.md)

## 13. エラー時の復旧方法

| 症状 | 確認・対処 |
|---|---|
| LINE の検証が 302 | 「LINE接続チェック」の「Web アプリの反映状況」が【NG】なら旧コードが動いています。ウェブアプリを「新バージョン」で更新し、1〜2分待ってから疎通テストを実行してください |
| 疎通テストは失敗だが GAS 受信記録は OK | GAS は処理しています。デプロイが新バージョンか確認してください |
| 疎通テストは成功だが GAS 受信記録が NG | Webhook URL が別のデプロイを指しています。ID管理の `GAS_WEBAPP_URL` と LINE の設定を一致させてください |
| まず確認すること | 「システム管理 → エラーログを開く」で、未対応の FATAL / ERROR を確認します |
| 返信が来ない | 「接続・設定診断」でトークン・Webhook の利用（オン）・応答モード（Bot）を確認します。本体GASの「実行数」でエラーを確認します |
| 特定の利用者に自動応答しない | 「自動返信有効」が FALSE です。「お問い合わせ → 自動返信の状況」で判定行を確認し、対応が済んでいればその行を TRUE にします |
| 問い合わせが保存されない | 受付返信が LINE に拒否されています。実行ログの `webhook.event_failed` を確認してください（応答トークンの期限切れなど） |
| 「設定が不足しています」 | 表示されたキーを、ID管理シートまたはスクリプトプロパティに入力します |
| 管理メニューが動かない | [docs/sheet-admin.md](docs/sheet-admin.md#トラブルシューティング) |

その他: [docs/operations.md](docs/operations.md#障害時の確認手順)

## 14. メッセージの文言（文体・絵文字・変更方法）

利用者に表示するメッセージは、「高級ホテルのコンシェルジュ」をイメージした上品で簡潔な文面にそろえています。文言だけを変更しており、イベント処理・ボタン・postback・自動返信の TRUE/FALSE 制御・オペレーター切替は変えていません。

### 文体のルール

- 丁寧で自然な日本語にします。過度に堅い表現は避け、「くださいませ」「承ります」「でございます」は自然な箇所にだけ使います。
- 通常の案内は1〜3文にします。ボタン付きのメッセージは短い案内文だけにします。
- **ボタン（クイックリプライ）に表示される選択肢を、本文で繰り返しません。** 本文では「下記より」と案内します。
  - 例（お問い合わせ）：`🚁 お問い合わせありがとうございます。` / `ご希望の内容を下記よりお選びくださいませ。`
- ボタンがないメッセージで他の操作を案内するときは、「メニューの「お問い合わせ」より」のように場所を書きます。
- 予約・決済などの重要な通知（通知テンプレート）は、予約ID・日時などを省略せず、見出しと改行で整理します。
- 準備中の機能（URL 未設定のページ）は「現在準備中でございます」と案内し、ページがあるかのような案内はしません。
- 対応期限（○時間以内など）は、営業時間が確定するまで約束しません。

### 絵文字のルール

- 各メッセージに、内容に合う絵文字を **1〜3種類** 入れます。絵文字は連続させません。
- 主な使い分けは次のとおりです。

| 絵文字 | 用途 | 絵文字 | 用途 |
|---|---|---|---|
| 🚁 | フライト・ご案内全般 | ✨ | 特別な体験・プラン |
| 📩 | お問い合わせ・メッセージ | 📅 / 🗓️ | 日程・変更 |
| 🔖 | 予約番号・受付ID・予約確認 | 🌤️ | 天候・運航 |
| 💳 | 決済 | 💬 | オペレーター |
| ✅ | 完了・受付 | 📋 / 📍 | よくある質問・キャンセル／集合場所 |

### スプレッドシート管理の文言と GAS 固定の文言

| 種類 | 置き場所 | 変更方法 |
|---|---|---|
| 友だち追加のあいさつ、予約受付・確定・変更・キャンセル、決済完了、搭乗前日、運航変更、オペレーター対応開始 | 「通知テンプレート」シート（`WELCOME` `BOOKING_RECEIVED` `BOOKING_CONFIRMED` `BOOKING_CHANGED` `BOOKING_CANCELLED` `PAYMENT_COMPLETED` `FLIGHT_REMINDER` `FLIGHT_CHANGE` `OPERATOR_START`） | シートの「本文」を編集（コード変更・デプロイ不要）。`有効`=ON のものだけ使います |
| FAQ の回答 | 「FAQ」シート | シートの「回答」を編集（デプロイ不要） |
| リッチメニューの準備中案内（任意） | 「通知テンプレート」に `MENU_PENDING_BOOKING` などを ON で追加すると、GAS の文面より優先 | シートで追加・編集 |
| お問い合わせの案内、入力案内、受付完了、キーワード応答、準備中案内、FAQ メニュー、一致しないときの案内、テキスト以外への返信、予備の文面 | GAS のコード（下表） | コードを編集 → テスト → デプロイ |

- **シートの文面が優先**です。GAS の文面は、テンプレートが OFF・未登録のときの予備です。
  - あいさつ（`WELCOME`）は、OFF のとき GAS の予備の文面を送ります。
  - オペレーター対応開始（`OPERATOR_START`）も、OFF のとき GAS の予備の文面を送ります。
  - 予約・決済などの通知は、OFF のとき**送信しません**（送信ログに「テンプレート無効」と記録）。現在 `BOOKING_CHANGED` `BOOKING_CANCELLED` `PAYMENT_COMPLETED` `OPERATOR_START` は OFF です。
- 差し込み変数は `{{予約ID}}` `{{搭乗日時}}` `{{搭乗日}}` `{{時間帯}}` `{{プラン名}}` `{{人数}}` `{{集合場所}}` です。`OPERATOR_START` では `{{受付ID}}` も使え、ない場合は末尾に `🔖 受付ID：…` が付きます。
- 通知に予約確認 URL（ID管理 `BOOKING_CONFIRM_URL`）が設定されている場合は、本文の後に「🔖 ご予約の詳細は、下記よりご確認いただけます。」のボタンが付きます。
- GAS は既存のテンプレート・FAQ の本文や ON/OFF を上書きしません。「シート列・設定行の補完」は、行がないテンプレートだけを OFF で追加します。
- `07_Notification.gs` の `DEFAULT_TEMPLATES`（行がないときに追加する文面）は、管理台帳の承認済み文面（2026-10-28 時点）と同じです。

GAS 固定の文言の場所：

| 文言 | ファイル・名前 |
|---|---|
| お問い合わせ開始（種別選択） | `05_Inquiry.gs` `MSG_INQUIRY_MENU` |
| 種別選択後の入力案内・フライト予約の案内・受付完了 | `05_Inquiry.gs` `INQUIRY_GUIDE_TEXT` / `FLIGHT_GUIDE_TEXT` / `inquiryReceivedText_` |
| 予約確認（予約ID入力・本人確認・予約内容・変更／キャンセルの案内） | `06_Reservation.gs` `RSV_TEXT` / `buildReservationCard_` |
| 入力の取り消し・テキスト以外への返信 | `01_Webhook.gs` `MSG_INQUIRY_CANCELLED` / `MSG_NON_TEXT` |
| キーワード応答（予約・プラン・料金・チャーター・天候・キャンセル・集合場所）、FAQ メニュー、一致しないとき | `04_FAQ.gs` `INTENT_TEXT`（`*_PENDING` / `*_NO_PAGE` は URL 未設定時の文面） |
| 要有人確認の FAQ に付ける一文 | `04_FAQ.gs` `faqAnswerMessage_` |
| リッチメニューの準備中案内・リンク案内 | `08_RichMenu.gs` `RICHMENU_PENDING_TEXT` / `buildRichMenuPendingReply_` |
| URL 未設定時の既定の準備中案内 | `02_LineApi.gs` `buildLinkMessage_` |
| あいさつの予備 | `00_Config.gs` `DEFAULT_WELCOME_MESSAGE` |
| オペレーターに相談の案内の予備 | `12_Operator.gs` `DEFAULT_OPERATOR_PROMPT_TEXT` |

自動返信有効=FALSE の顧客（オペレーター対応中を含む）には、GAS は何も送りません（停止中のお知らせも送りません）。担当者が LINE Official Account Manager のチャットから返信します。

### 文言の変更方法

1. シートで管理している文言は、シートを編集するだけで次の送信から反映されます。
2. GAS 固定の文言は、上表のファイルを編集し、文体・絵文字のルールに合わせます。
3. `npm test` を実行します。`tests/messages.test.js` が文言を検査します。文言を変えたときは、このテストの期待値も更新してください。
   - お問い合わせ画面の本文に選択肢が含まれていないこと
   - ボタンのラベル・postback が変わっていないこと
   - 絵文字の種類（1〜3）・連続、LINE の文字数制限（テキスト5000字、ボタン本文160字、ラベル20字、クイックリプライ13件）
4. 本番に反映します（下記）。

### テスト方法

```bash
npm test                              # すべてのモックテスト
node --test tests/messages.test.js    # 文言の回帰テストのみ
```

モックテストは、実際の LINE での表示を保証しません。反映後はテスト用アカウントで、お問い合わせ・FAQ・リッチメニュー・オペレーター切替を確認してください。

### GAS のデプロイ方法

本番への反映は、管理者の承認後に行います。

```bash
clasp push                    # 本体GAS（スクリプトID 1zlkPtaZ…ff。.clasp.json の rootDir は src/gas）
clasp deploy -i <既存のデプロイID> -d "文言改善"   # 既存のウェブアプリを新バージョンで更新（URL は変わらない）
```

- `clasp deploy` に `-i`（既存のデプロイID）を付けないと、新しい URL のデプロイが作られます。Webhook URL が変わってしまうため、必ず既存のデプロイを更新してください。
- エディタで行う場合は、デプロイ → デプロイを管理 → 既存のウェブアプリを編集 → 「新バージョン」を選びます。
- 反映後は管理メニュー「LINE接続チェック」で、「Web アプリの反映状況」が【OK】（`APP.BUILD` と一致）になることを確認します。
- 管理メニュー用GAS（スプレッドシートの Apps Script）は、今回の文言変更では更新不要です。

### 必要なスクリプトプロパティ

文言の変更で新しく必要になるプロパティはありません。本体GASに必要なプロパティ名は [4章](#4-スクリプトプロパティ一覧本体gas) のとおりです（`LINE_CHANNEL_ACCESS_TOKEN` `SPREADSHEET_ID` `ADMIN_USERS`、予約通知を使う場合は `RESERVATION_WEBHOOK_SECRET` など）。値（トークン・シークレット）はリポジトリ・シート・チャットに書かず、スクリプトプロパティにだけ保存します。

### よくあるトラブルと確認方法

| 症状 | 確認すること |
|---|---|
| 文言が古いまま | Web アプリが新バージョンで更新されているか（「LINE接続チェック」の反映状況）。シート管理の文言なら、テンプレートの `有効` が ON か |
| 予約・決済の通知が届かない | テンプレートが OFF（送信ログの結果「テンプレート無効」）か。顧客がブロック中（「対象外(ブロック)」）か |
| `{{予約ID}}` などがそのまま表示される、空欄になる | 変数名の誤り（全角・空白）か。予約サイトからのイベントにその項目が含まれているか |
| ボタンが表示されない | ラベル20字・13件の上限を超えていないか。FAQ の「質問・キーワード」の最初の区切りまでがボタン名になります |
| 「現在準備中」と表示される | ID管理に該当ページの URL（`BOOKING_SITE_URL` `BOOKING_CONFIRM_URL` `PLAN_LIST_URL` `CHARTER_URL`）が未設定。設定後、リッチメニューは「リッチメニュー登録・更新」の再実行が必要 |
| 特定の顧客にだけ返信しない | 「問い合わせ管理」の「自動返信有効」が FALSE（「お問い合わせ → 自動返信の状況」で確認） |
| 誰にも返信しない | 「接続・設定診断」でトークン・Webhook の利用（オン）を確認。「エラーログ」シートを確認 |
